1. Arquitectura actual del módulo

El módulo de operaciones está en lib/features/operaciones/ y se apoya en cuatro componentes principales:

Archivo Responsabilidad
servicios/osrm_service.dartLlama a la API de OSRM, parsea la ruta real, calcula ETA. Tiene fallback Haversine.
servicios/vehiculos_service.dartGestiona ambulancias en Firestore. Contiene el AlgoritmoDespacho que ordena ambulancias por ETA.
servicios/cad_simulation.dartSimula el movimiento GPS de ambulancias en Guadalajara (modo demo). Tick cada 2,5 s.
modelos/vehiculo_cad.dartModelo de datos del vehículo: coordenadas, estado, tipo (SVB/SVA), tripulación, rumbo.
pantallas/cad_operaciones_screen.dartUI del Centro de Coordinación de Ambulancias. Mapa flutter_map + OpenStreetMap tiles.
Librería de mapas flutter_map v7.0.2 + latlong2 v0.9.1

Las baldosas del mapa provienen de tile.openstreetmap.org. Las rutas se dibujan como polilíneas con la geometría real devuelta por OSRM (o 3 puntos si hay fallback).

2. Cómo se calcula la distancia hoy

Cuando hay que despachar una ambulancia a un aviso, el sistema hace lo siguiente:

Aviso creado (lat/lng)
→
Lista de ambulancias disponibles
→
Llamada OSRM × N (en paralelo)
→
Ordenar por ETA
→
Priorizar SVA para PCR/IAM
→
Recomendación al operador

Paso 1 — Llamada a OSRM

Para cada ambulancia disponible se construye esta URL:

GET https://router.project-osrm.org/route/v1/driving/
    {longitud_ambulancia},{latitud_ambulancia};
    {longitud_aviso},{latitud_aviso}
    ?overview=full&geometries=geojson&steps=false

OSRM devuelve tres datos clave:

  • distance — metros por carretera real (sí respeta sentidos y vías)
  • duration — segundos estimados según el perfil de velocidad del grafo OSM
  • geometry — array de coordenadas GeoJSON con la polilínea exacta de la ruta

Paso 2 — Transformación interna

// osrm_service.dart · líneas 52-66
final distanceKm  = distanceM / 1000;    // metros → km
final etaMinutes  = durationS / 60;      // segundos → minutos
// Los waypoints (100-300 puntos) se pasan directamente al PolylineLayer del mapa

Paso 3 — Ordenación por ETA

// vehiculos_service.dart · líneas 141-146
resultados.sort((a, b) {
  if (a.compatibleTipo != b.compatibleTipo) {
    return a.compatibleTipo ? -1 : 1;  // SVA sube si es PCR/IAM
  }
  return a.ruta.etaMinutes.compareTo(b.ruta.etaMinutes);
});
Lo que SÍ funciona bien

Cuando OSRM responde correctamente, la ruta sí respeta calles, sentidos únicos y el trazado real de la carretera. El mapa muestra la polilínea exacta. La ordenación por ETA es correcta.

3. Qué es OSRM y cuál es su fiabilidad real

OSRM (OpenStreetMap Routing Machine) es un motor de rutas de código abierto que usa el grafo de carreteras de OpenStreetMap. El proyecto usa el servidor público gratuito:

https://router.project-osrm.org  ← demo server de los creadores de OSRM
AspectoValoraciónDetalle
Sentido de circulación Sí respeta Usa el atributo oneway de OpenStreetMap. Nunca calculará una ruta contramano.
Calles reales Sí respeta El motor sólo navega por vías existentes en el grafo OSM de España.
Señales de dirección Parcialmente Respeta restricciones de giro y prohibiciones codificadas en OSM. Si faltan en el mapa, no las aplica.
Tráfico en tiempo real No OSRM usa velocidades estáticas del perfil "driving". No hay datos de tráfico en vivo.
Uptime del servidor público Sin garantía Es un servidor demo. No hay SLA, puede tener cortes o rate limiting sin aviso.
Latencia media ~200-800 ms Varía según carga del servidor. Con 5 ambulancias en paralelo puede saturarse.
Calidad datos España Alta OpenStreetMap España tiene muy buena cobertura urbana. Guadalajara concretamente está bien mapeada.
Coste Gratis El servidor público es gratuito pero no apto para producción crítica.
Conclusión sobre OSRM público

OSRM como tecnología es sólido y fiable. El problema no es el motor, sino que se usa el servidor demo público, que no está pensado para aplicaciones en producción. Para un servicio de emergencias, esto es un riesgo real.

4. El problema del fallback Haversine — el origen del "no respeta carreteras"

Cuando OSRM falla (timeout de 8 s, error de red, rate limiting), el sistema cae en este fallback:

// osrm_service.dart · líneas 74-90
static RouteResult _fallback(LatLng origen, LatLng destino) {
  final straight = _haversineKm(origen, destino);  // distancia en línea recta
  final roadDist = straight * 1.38;                // × 1.38 para simular carretera
  final eta = (roadDist / 55) * 60;                // 55 km/h de media

  // ⚠️ Punto intermedio ALEATORIO — cada cálculo da un resultado distinto
  final mid = LatLng(
    (origen.latitude  + destino.latitude)  / 2 + (Random().nextDouble() - 0.5) * 0.003,
    (origen.longitude + destino.longitude) / 2 + (Random().nextDouble() - 0.5) * 0.003,
  );
  return RouteResult(
    distanceKm:  roadDist,
    etaMinutes:  eta,
    waypoints:   [origen, mid, destino],  // ← sólo 3 puntos = línea recta diagonal
    isFallback:  true,
  );
}
Problema crítico La línea recta en el mapa es señal de fallback activo

Cuando el operador ve una línea diagonal ignorando calles, significa que OSRM no respondió a tiempo y se usó Haversine. Esto ocurre con más frecuencia de lo deseable porque el servidor público puede tardar o fallar bajo carga.

Otros problemas del fallback

  • El punto intermedio es aleatorio en cada llamada — si se recalcula, la ruta en pantalla salta a una posición diferente aunque la ambulancia no se haya movido.
  • El factor × 1.38 es una estimación genérica. Para ciudades con mucho viario irregular (casco antiguo de Guadalajara), el factor real puede ser 1.5-1.7.
  • Los 55 km/h de media para emergencias en ciudad es razonable, pero no tiene en cuenta que en el centro histórico la velocidad máxima legal es 30 km/h.
  • El isFallback: true existe en el modelo pero la UI no muestra ningún aviso al operador de que la ruta mostrada es una estimación.

6. Problemas identificados

P1 · Crítico Servidor OSRM público — no apto para producción

router.project-osrm.org es un servidor demo sin SLA. Puede caer, aplicar rate limiting o aumentar latencia sin previo aviso. Con 5 ambulancias calculando en paralelo (5 peticiones simultáneas), la probabilidad de que al menos una caiga en fallback es alta.

Riesgo: En el momento de un despacho real, la ambulancia recomendada puede basarse en distancias Haversine incorrectas → el operador podría enviar la ambulancia equivocada.

P2 · Crítico Fallback silencioso — el operador no sabe que la ruta es una estimación

Cuando se usa Haversine, el campo isFallback: true está en el objeto RouteResult pero la UI del CAD no muestra ningún aviso. El operador ve una línea diagonal en el mapa y puede confundirla con una ruta real.

P3 · Medio Punto intermedio del fallback es aleatorio

El midpoint usa Random().nextDouble(). Si la misma ruta se recalcula (por cambio de estado del vehículo), la polilínea "salta" a una posición diferente en el mapa. Esto es visualmente confuso y puede alarmar al operador innecesariamente.

P4 · Medio No hay datos de tráfico en tiempo real

OSRM usa velocidades estáticas del perfil de conducción OSM. Un aviso en hora punta en la Avenida del Ejército puede tener un ETA real muy diferente al calculado. La diferencia puede ser de 2-4 minutos en ciudad, que en emergencias es significativa.

P5 · Medio Sin optimización multi-aviso simultáneo

Si hay dos avisos activos a la vez, el algoritmo los procesa independientemente. Es posible que asigne la misma ambulancia (la mejor en ETA) a ambos, dejando un aviso sin cobertura. No hay lógica de asignación óptima global.

P6 · Menor GPS de simulación patrulla por waypoints hardcodeados

Las rutas de patrulla del modo demo tienen waypoints fijos en cad_simulation.dart. No son rutas OSRM, así que en la simulación los vehículos "teleportan" entre puntos en lugar de seguir calles reales. No afecta a producción pero da una impresión visual incorrecta.

7. Mejoras propuestas

01

Autoalojar OSRM con datos de España

Descargar el extract de España de Geofabrik y arrancar OSRM en un VPS o Docker. Latencia <20 ms, sin límites de tasa, sin dependencia externa.

Impacto: Alto Esfuerzo: Medio
02

Mostrar aviso al operador cuando hay fallback

Leer isFallback del RouteResult y mostrar un chip naranja "⚠️ ETA estimado" en la tarjeta de la ambulancia y un trazo discontinuo diferente en el mapa.

Impacto: Alto Esfuerzo: Bajo
03

Eliminar el punto intermedio aleatorio del fallback

Usar siempre el punto central exacto (lat1+lat2)/2, (lng1+lng2)/2 sin desplazamiento aleatorio. La ruta será una línea recta pero consistente y predecible.

Impacto: Medio Esfuerzo: Mínimo
04

Usar OSRM Table API para múltiples ambulancias

En lugar de N peticiones en paralelo, usar /table/v1/driving que calcula distancias de N orígenes a 1 destino en una sola petición. Mucho más eficiente y menos probable de saturar el servidor.

Impacto: Alto Esfuerzo: Medio
05

Integrar datos de tráfico de la DGT

La DGT tiene un API abierto de incidencias de tráfico (DATEX II). Cruzar el ETA de OSRM con el estado del tráfico en la ruta para ajustar el tiempo estimado en horas punta.

Impacto: Medio Esfuerzo: Alto
06

Bloquear ambulancias ya asignadas en despacho múltiple

Cuando hay varios avisos activos, excluir ambulancias que ya están en en_route de los candidatos de nuevos avisos. Implementar asignación óptima greedy por ETA considerando todos los avisos pendientes.

Impacto: Alto Esfuerzo: Medio
07

Rutas de patrulla generadas por OSRM (modo demo)

En la simulación, en lugar de saltar entre waypoints hardcodeados, calcular rutas OSRM para las patrullas. Los vehículos seguirán calles reales en la demo, dando una imagen más realista al operador.

Impacto: Bajo Esfuerzo: Medio
08

Historial de ETAs reales vs. estimados

Guardar en Firestore el ETA calculado y la hora real de llegada al aviso. Con 20-30 registros se puede calibrar el factor de velocidad (actualmente fijo en 55 km/h) por zona, turno o tipo de vía.

Impacto: Medio Esfuerzo: Medio

Recomendación de migración

La ruta óptima a corto plazo es: mantener la lógica actual de OSRM pero apuntar a un servidor propio. Solo hay que cambiar static const String _baseUrl en osrm_service.dart (línea 32). El resto del código no necesita modificarse — toda la integración ya está correctamente implementada.

Resumen ejecutivo

Qué está bien
  • OSRM sí respeta calles y sentidos de circulación cuando funciona correctamente.
  • El algoritmo de despacho es sólido: paralelo, ordenado por ETA, con prioridad de tipo SVA.
  • El modelo de datos (VehiculoCAD) está bien estructurado y permite ampliar fácilmente.
  • El mapa muestra la geometría real de la ruta (no sólo origen-destino).
Qué hay que cambiar ya
  • Migrar de router.project-osrm.org a un servidor OSRM propio.
  • Mostrar en la UI el indicador isFallback para que el operador sepa cuando el ETA es estimado.
  • Eliminar el Random() del midpoint del fallback para que la ruta sea consistente.
